# Procure Sherpa v2.4 — Completion Ledger

Audited 2026-11-01. **Every row below was read out of the code in `src/` and out of the live output of the gate tools named in "How to re-verify"** — not out of `IMPROVEMENT_ROADMAP.md`, not out of `docs/v2.4-delivery-report.md`, not out of `README.md`. Where a row rests on a test, the test is named and the reason it could fail is stated. Where a row rests on content that no test touches, the row says so and drops to YELLOW. Counts were recomputed from the built artifact (`ProcureSherpa-v2.0.html`, build stamp `47ac14587fdd`, drift-checked clean against the 177 fragments in `src/manifest.txt`), not quoted from documentation.

## Legend

- **GREEN** — the requirement is implemented AND an actual assertion exercises it. The row names the implementing file and line, and names the gate or test that would fail if the behaviour broke. If nothing asserts it, the row is not GREEN no matter how complete the code looks.
- **YELLOW** — present but partial, scaffolding only, unverified, or verified only by an assertion that could not fail. The row says which.
- **RED** — absent.

## How to re-verify

| Evidence type | Command |
| --- | --- |
| Every gate's summary (routes, calculator assertions, layout, integrity, a11y, perf, i18n) | `npm run qa` prints all of them (slow); a single number is cheaper: `node tools/smoke.mjs`, `node tools/test_integrity.mjs`, `node tools/perf_check.mjs`, `node tools/a11y_audit.mjs`, `node tools/test_calcs.mjs`, `node tools/test_calc_values.mjs` |
| Content registries actually registered, item by item | `node tools/inventory.mjs` (and `node tools/dump_index.mjs` for titles). Since Cycle 1 this reads the same two registration paths `check_rels` does, through `registryFromSource()` in `tools/lib.mjs`, and prints `CALC (19)`; it used to print `CALC (0)` because it matched on the full path `calcs/20a_…` against `/^2\d/` |
| Relationship / link integrity | `node tools/check_rels.mjs` |
| A route's rendered size and runtime errors | `node tools/smoke.mjs`. The threshold is no longer a character count: `tools/page_contract.mjs` states what a route must contain to count as rendered (LIBRARY ≥ 600 chars, WORKSPACE ≥ 250 chars *and* a way forward, STATE exempt; no not-found card, no sentinel leak, one visible h1) and the same contract is run by G7 in `test_integrity.mjs` and by `verify_deploy.mjs` |
| One registry or field read out of the artifact | `node -e` or a jsdom probe against `ProcureSherpa-v2.0.html` (see `tools/test_interactive.mjs` for the loading boilerplate) |
| Calculator value correctness | `node tools/test_calc_values.mjs` (hand-computed fixtures) and `node tools/test_calcs.mjs` (envelope/finite/required-field) |
| Utility/sanitiser behaviour on the shipped code | `node tools/test_unit.mjs` |
| Integrity gates G1–G23 | `node tools/test_integrity.mjs` |
| The exact content-count pins | owned by `tools/content_pins.mjs`; run inside `npm run qa` by G1/G16/G21/G22 and re-run against the served bytes by `node tools/verify_deploy.mjs` |
| Deploy verification (what only it can do: the served bytes carry this source tree's build stamp) | `node tools/verify_deploy.mjs` |
| Node version gate | `export NVM_DIR="$HOME/.nvm"; . "$NVM_DIR/nvm.sh"; nvm use 22` first — the repo refuses Node 20 |

## Cycle 2, Wave A: the curriculum now says what level it is written at

**Shipped 2026-11-01, when the curriculum held 28 functions.** Every Academy function - 34 today - carries one of three
levels — Foundation (9), Practitioner (12), Executive (7) — chosen by the altitude of
the decision the lesson prepares the reader for, not by seniority. The levels render on
the hub cards, state themselves on the function page, tag the nine learning paths, and
filter the curriculum through `#/academy?tier=practitioner` (a bookmarkable address, not
client state; an unknown level falls back to the full curriculum rather than emptying it).

**Why this exists.** The complaint this project keeps receiving from practitioners is that
the product is good for a first week and thin for a category manager, and the cause was
structural: one flat voice, 28 lessons with nothing on the page saying which altitude a
lesson was for, so the only way to find out was to open it. A label does not by itself make
the senior content exist — Modules 12-14 and the six deeper middle functions are Waves B
and C — but it makes what does exist findable, and it makes the remaining gap measurable
instead of anecdotal.

**How to re-verify.** `node tools/test_integrity.mjs` prints G23: every function carries a
named level, the split is pinned, the hub labels all 28 cards and filters correctly, the
function page states its level, and the paths are tagged. Mutation-proved: removing the tier
from `func-category-strategy` turned four assertions red naming the function; the source was
restored from `/tmp/19e_tier_backup.js` and the artifact rebuilt.

**Traded away, stated rather than silent:** ~5 KB of the 604 KB ADR-0002 transfer headroom
(three levels of labels and one filter card). The Gate chain also changed: `npm run qa` now
runs `build:min` after the relationship check so G20 compares two builds of the same sources
instead of a stale `dist/` — which is why the minified build appears mid-chain rather than only
inside `verify:min`.

### Cycle 8 addendum 14 — the review queue, or what a finished lesson is worth if nothing brings it back

**The gap.** The Academy recorded that a lesson had been read and whether its quiz was passed, then treated the curriculum like a list: a lesson studied in September was never mentioned again. For a learning portal that is the central failure mode, and no UI polish fixes it — the product needs a schedule.

**What shipped.** `PS.revise` (`src/core/03k_revision.js`) and the `#/revise` page (`src/pages/08i8_pages_revise.js`). A passed quiz (70% or more) puts a lesson on 7 / 21 / 60 / 180 day gaps; a shaky or missing quiz puts it on 3 / 14 / 45. Marking a review advances the ladder, so a lesson that keeps being revisited is asked about less often rather than sitting in the queue forever. Entry points: the Academy hub states what is due in its own summary block, the progress transcript carries a button, and `#/next-up` recommends the queue when something is overdue.

**Two decisions that were made deliberately.** (1) The timestamps live in a new `log` map inside the academy record rather than replacing `completed[id] = true`, because six other surfaces — badges, hub rails, the transcript, G24 and G27 — read that flag as truthy; changing its shape to an object would have been a behavioural edit spread across code that does not belong to this feature. (2) **Nothing is backdated.** Quiz records already carry an ISO date, so lessons passed last month arrive genuinely overdue. Completions written before dates existed carry no date at all: those are scheduled from today and labelled as such, on the page and in the count (`noDate`), never presented as though the app knew when they were read. The page also states that the intervals are a spaced-practice convention, not a measurement of this reader's forgetting curve.

**The gate earned its keep twice.** G11 refused the new route as unreachable — `#/revise` was only linked when something was already scheduled, so a first-time learner had no path to a page that would have told them to start studying. The hub line is now unconditional with three honest states. And G20 caught the stale minified build, as it does every tranche.

**Verification.** `npm run qa` exit 0 — **30 gates / 138 assertions**, layout **34/34** (two new DOM checks: the queue renders a heading and a way forward on an empty record; the hub carries the entry point), 86 smoke routes, 32 journey steps, a11y 0 findings over 65 routes, perf PASS at 871.5 KB gzipped committed (791.7 KB minified served), 201 fragments. Six new G27 assertions pin the arithmetic itself: a fresh record schedules nothing; a lesson studied two days ago is due tomorrow and not overdue; a lesson passed thirty days ago is due now, measured from the real date in the record; three marked reviews lengthen 7 → 21 → 60 days; two undated completions are counted as undated; and the page states the same numbers the scheduler computes.

### Cycle 8 addendum 16 — reflection: the answer record read back as judgement gaps, and a gate that had to learn what "coached" means

**What shipped.** `PS.reflection` (`src/core/03l_reflection.js`) and `#/reflection` (`src/pages/08ia_pages_reflection.js`). The quiz engine already stored, per question, the option the learner chose (`scores[funcId].answers[qIdx]`) and whether they reached the right answer only after the tactical tip (`recovered[qIdx]`). That is enough to state four distinct kinds of weakness — right first time, got there with coaching, still wrong, never attempted — without inventing a data model: the page ranks the **principles** the answers have not settled (each Academy question names one), lists the lessons to revisit ranked by what is open in them, and links every claim back into the practice tab. Entry points: the transcript (unconditional, so a fresh learner can see it exists), the review queue, and `#/next-up` when an answer is still wrong.

**Why not the mistakes map.** `PS.academy.getMistakeState` is transient — `clearMistake` runs when a question resolves and again on retry — so it reports only what is open mid-attempt, not history. Deriving the reflection from the durable answer record instead is what makes the numbers defensible after the fact.

**G31 was written because the first version of the test asserted the wrong thing.** Seeded "coached" as a wrong choice with the recovered flag set, and the summary reported 1 clean / 0 coached / 2 wrong. That was not a bug in the product: the engine records `recovered` only when the *final* answer is correct, so a coached question is a correct answer plus a flag. The seed was corrected to match the engine, and the five assertions now pin the real behaviour: no answers → no claimed weakness and a way to start; clean / coached / wrong separated exactly as the record supports; unanswered counted as open and never as a weakness, with untouched lessons absent from the list; ranking weight is 2 per wrong plus 1 per coached; the page states the same wrong count the record holds and explains its own derivation. Gate count 30 → **31**, assertions 139 → **144**.

**Also fixed in this pass:** a scripted edit to the transcript buttons emitted a duplicated link and a stray `+  +`, which G2/G3 caught as a `NaN` leak on `#/academy-progress` before it could ship — the second time this cycle a scripted patch damaged a file and a gate caught it rather than the diff being eyeballed.
