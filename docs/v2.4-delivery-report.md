# ProcureSherpa v2.4 - Delivery Report

**Date:** 2026-10-20
**Baseline:** `ea624ff^` (the commit before the revamp)
**Head:** the current `main`
**Live:** https://procuresherpa.vercel.app

This is the closing document for the v2.4 revamp. It records what was
built, what it cost, what was tested, and what is still open. It is
written from the build and the test output rather than from the plan,
because the plan was wrong in several places and the differences
matter.

## 1. The one-paragraph version

The application was green in CI while being broken in a dozen places.
The maturity check rendered nothing and threw; the lifecycle page
promised twenty-one stages and showed none; the skill assessment
showed "undefined%" for an 80% score; the KPI calculator inverted its
RAG band; 27 of 41 cross-tool links carried no data; a restored backup
silently reverted to the example data. All of that is fixed. The
navigation was rebuilt from five sections of 33 items into a menu scoped by
the track you chose, 26 items for a learner and 30 for a practitioner,
the curriculum grew from 8 modules and 19 functions to 11 and 28, and
eight workbenches were added so the toolkit can hold the user's own
suppliers, contracts, catalogue, bids, receipts and budgets instead of
only teaching about them. The performance ceiling, which had been a
number nobody derived from anything, is now derived from "3 seconds on
4G" and cannot drift away from its reason.

## 3. The navigation, before and after

| | Before | After |
|---|---|---|
| Sections | 5 | **5 in the Learn view, 6 in the Work view** |
| Items | 33 flat, then 39 flat | **26 in the Learn view, 30 in the Work view** |
| Scoping | None | **By the profile track, with a Learn / Work switch** |
| Present on the landing page | No | **Yes** |
| Active-state coverage | 25 of 33 | **Every item, in both views** |
| System pages | Four loose chips, no label | **Labelled "System" strip** |
| Section behaviour | All expanded, long scroll | **Opens the current section, rest collapsed** |

The navigation is **scoped by the profile's track**, which the
profile has carried since it was added and which had done nothing but
change one line of text. A learner sees **Start, Learn, Library, Look
It Up, My Work** - 5 sections, 26 items. A practitioner sees **Start,
Workbench, Toolkit, Library, Look It Up, My Work** - 6 sections, 30
items. The reference library is shared, because the Academy is taught
through it. A **Learn / Work** switch in the sidebar changes the track,
writing the same profile field the profile modal writes, so there is one
source of truth. And the current route always wins: a page whose section
your track hides has that section shown for that visit, so the menu is
never a dead end.

## 5. Budget ledger

The plan's binding limit was a 1,300 KB script ceiling. The plan was
wrong about where that ceiling came from, and this is the record of
what was actually spent.

| | Readable | Minified | Gzipped |
|---|---|---|---|
| Baseline (`ea624ff^`) | 1,271 KB | 1,232 KB | 446 KB |
| Head | **1,976 KB** | **1,620 KB** | **546 KB** |
| Delta | +679 KB | +376 KB | **+93 KB** |
| Ceiling | - | - | **1,152 KB** |
| Headroom | - | - | **606 KB** |

**The ceiling was wrong.** ADR 0001 said "3 seconds on 4G". The
implementation picked 1.5 Mbps, which is 3G territory, and turned that
into a 576 KB ceiling. It was six times tighter than the trigger it
came from, and it was a number nobody could derive. It is now 3 Mbps
- still well below the 10 to 25 Mbps median Ookla reports for 4G -
which gives 1,152 KB. `build.mjs`, `tools/perf_check.mjs` and
`tools/build_min.mjs` all compute it from seconds times rate, so the
ceiling and its reason cannot drift apart again.

The plan's reclaim table predicted ~45-55 KB of savings from
refactoring. The actual reclaim was smaller, and it did not matter,
because the ceiling was never the binding constraint. **The real
constraint on this product is now the reader's time and the
maintainability of the code, not the byte ceiling.** 606 KB of
gzip headroom is roughly 2.1 MB of further source.

### Blocked, and not fixable from here

| Issue | Impact | Cause | What is needed |
|---|---|---|---|
| GitHub Actions fails on every push | The hosted runner never runs the gate | Account billing: *"recent account payments have failed or your spending limit needs to be increased"* | Settings -> Billing and plans. The last scheduled run passed on 2026-10-19 |
| Vercel Git integration is blocked on every push | Pushes do not auto-deploy | Hobby plan `TEAM_ACCESS_REQUIRED`: the commit author has no Vercel account, and Hobby forbids team members | Link GitHub to the Vercel account, or create a token and run `gh secret set VERCEL_TOKEN`. `npm run deploy` works meanwhile |

**Neither affects the local gate or the release path.** `npm run qa`
is the same gate CI runs, and `npm run deploy` refuses to publish
anything that has not passed it. The release does not depend on the
hosted runner being available.

### Known and accepted

- The searchable content is English-authored. The application shell is
  fully translated across English and Spanish.
- Credentials are deliberately not issued. ProcureSherpa is not a
  legally authorised credential issuer and says so.
- The workbenches are workpapers, not a system of record. The receipt
  workpaper finds the variance and does not release a payment. The
  approvals workbench records a delegation of authority and does not
  route an approval or block a purchase. The RFx workbench produces an
  award recommendation and does not constitute a tender.
- There is no `og:image`, because generating an honest 1200x630 asset
  would mean a rasterizer dependency for one image.

### External dependencies

**None.** No server, no APIs, no runtime dependencies. `dependencies`
is empty and stays empty. `terser` is the only dev-dependency and it
never reaches a user.

## 9a. Wave 7 - the second review

Three things came out of a second pass over the product, and all three
were wrong in ways the first pass had missed.

### The curriculum was scattered, and the gate protected it

The Academy reordered its modules by the profile role. A buyer saw
**Module 7, 9, 2, 1, 3, 4, 5, 6, 8, 10, 11** while every badge still
read its own number. Only the default profile got 1 to 11, and the
default is what every screenshot and every check had used.

The root cause was not the reordering, it was the method. The gate
G13 was written from the feature rather than from the requirement, so
it asserted that the role *reordered* the curriculum - it protected
the defect. G13 now states the requirement in the requirement's words.

| | Before | After |
|---|---|---|
| Module order | Role-dependent, scattered for 4 of 5 roles | **1 to 11, always** |
| Role's effect | Reordered the curriculum | **Recommends modules, in module order** |
| Resume target | Last opened, so it never moved | **First uncompleted function** |
| Expert learning path | 4, 10, 10, 10, 8, 8 | **4, 8, 8, 10, 10, 10** |
| All-modules table | Grouped by track | **Sorted by module number, with a Module column** |

### The menu had a two-option field and ignored it

The profile has carried a `track` since it was added. It changed one
line of text. The sidebar was a flat 39 items for everybody.

| | Learn view | Work view |
|---|---|---|
| Sections | Start, Learn, Library, Look It Up, My Work | Start, Workbench, Toolkit, Library, Look It Up, My Work |
| Items | **26** | **30** |

The reference library is shared between the two views on purpose: the
Academy is taught through the SOPs, templates and calculators, and
every Academy function links into them. A **Learn / Work** switch in
the sidebar writes the same `profile.track` field the profile modal
writes, so there is one source of truth. The current route always
wins, so the menu is never a dead end.

This changed a documented rule rather than breaking one. `src/README`
said not to reintroduce a hub-switcher, and I had been quoting that
rule as though it came from ADR 0001. It did not - ADR 0001 is about
the single-file architecture and says nothing about the sidebar. The
rule's actual reasons were two specific implementation failures. It
is now rewritten with what it should have said, and the reason it
changed is recorded there rather than quietly overwritten.

### The explanation did not carry its example

A case study lived in the 'Think' tab, so somebody reading how landed
cost works never met an example of landed cost working. The example
is now in the 'Learn' tab, in the middle of the explanation, and the
worked example links to the calculator with `?example=1` so the
reader arrives at a finished calculation rather than an empty form.

The calculators already had curated example data and a Load example
button. What was missing was the ability to explore: **Random
values** perturbs the example by enough to change the answer and
little enough that the figures still look like procurement, while
respecting every rule the field declares.

### What the tests caught

- **G11, the reachability gate**, collected its inbound links from the
  rendered sidebar, so scoping the menu made the three workbench
  routes look like orphans. A route is reachable if it is reachable in
  the view it belongs to, so the gate now checks both views.
- **Seven navigation icons became literal question marks.** The file
  was written through a PowerShell pipe whose encoding was not UTF-8,
  and it ate the Unicode symbols. The page still rendered and every
  test still passed; the sidebar just looked like it had a font
  problem. The icons are Unicode escapes now, and a gate fails the
  build on a question mark where a symbol belongs.
- **The navigation was built once at boot and never rebuilt on
  navigation.** The rule that the current route always wins did not
  work: a first load of any workbench page had a menu that did not
  contain the page. The cause of my missing it is the more interesting
  part: the test for the rule called `PS.buildNav()` by hand before it
  looked at the menu, so it passed while the product was broken. The
  test was checking that the function worked, not that the product
  worked. The gate now sets the hash and lets the router do the work,
  and a separate gate walks every route in both views to check that
  the section owning the page is on screen while you are on it.
- **A dead call to a deleted function** was left in the Academy hub.
  It worked by accident, because the function was gone. It read like
  the reordering was still there, which is exactly the kind of line
  somebody re-enables a year later without meaning to.

## 10. What I would do next

1. **The Library Hub.** The Operations Hub was derived from the
   registry, which fixed its coverage, but the nine content types are
   still nine separate list pages. One filterable cross-type library
   with a facet for type, domain, and lifecycle phase would be the
   single most useful addition left, and the registry already has
   everything it needs.
2. **Print stylesheet for the workbenches.** The records export to
   CSV but not to a paper workpaper. A procurement file that has to be
   printed for an audit is a real use case.
3. **The sandbox engine.** Eleven hand-written crisis sandboxes in
   `08g1` are the largest remaining duplication in the codebase. The
   plan called for collapsing them into one declarative table and one
   renderer. It is worth roughly 25 KB and would make adding the
   twelfth one a data change rather than a code change.
4. **Making the Vercel path automatic.** Every one of the eleven
   deploys in this revamp was a manual `npm run deploy` from a
   git-free staging copy. It works, but it is a person remembering to
   run a command, and the Git integration should be the normal path.
