**Date:** 2026-10-20
**Baseline:** `ea624ff^` (the commit before the revamp)
**Head:** the current `main`
**Live:** https://procuresherpa.vercel.app

This is the closing document for the v2.4 revamp. It records what was
built, what it cost, what was tested, and what is still open. It is
written from the build and the test output rather than from the plan,
because the plan was wrong in several places and the differences
matter.

> **Re-measured 2026-11-01.** The build kept moving after this report was
> filed, and `tools/check_drift.mjs` now measures the documents against
> the source, so the counts, sizes and gate results quoted below are the
> ones the current tree prints rather than the ones remembered on
> 2026-10-20. Where a figure is deliberately historical - the baseline
> sizes, the wave table, the measurements ADR 0002 dates to the revamp -
> it says so. Anything the tools print live is quoted from the tool, and
> the tool wins.

> **Re-measured again 2026-11-02, for v2.5.** The same convention applies to
> the numbers this pass produced: the Academy is 34 functions in 13 modules

## 1. The one-paragraph version

The application was green in CI while being broken in a dozen places.
The maturity check rendered nothing and threw; the lifecycle page
promised twenty-one stages and showed none; the skill assessment
showed "undefined%" for an 80% score; the KPI calculator inverted its
RAG band; 27 of 41 cross-tool links carried no data; a restored backup
silently reverted to the example data. All of that is fixed. The
navigation was rebuilt from five sections of 33 items into a menu scoped by
the track you chose, 26 items for a learner and 30 for a practitioner,
the curriculum grew from 8 modules and 19 functions to 11 and 28, and
eight workbenches were added so the toolkit can hold the user's own
suppliers, contracts, catalogue, bids, receipts and budgets instead of
only teaching about them. The performance ceiling, which had been a
number nobody derived from anything, is now derived from "3 seconds on
4G" and cannot drift away from its reason.

your track hides has that section shown for that visit, so the menu is
never a dead end.

## 5. Budget ledger

The plan's binding limit was a 1,300 KB script ceiling. The plan was
wrong about where that ceiling came from, and this is the record of
what was actually spent.

| | Readable | Minified | Gzipped |
|---|---|---|---|
| Baseline (`ea624ff^`) | 1,271 KB | 1,232 KB | 446 KB |
| Head, as re-measured 2026-11-01 | **1,978 KB** | **1,620 KB** | **547 KB** |
| Delta | +707 KB | +388 KB | **+101 KB** |
| Ceiling | not gated | not gated | **1,152 KB** |
| Headroom | - | - | **605 KB** |

The minified build is the one that actually ships, and it is gated
separately: `tools/build_min.mjs` reports 485 KB gzipped against a
deployed ceiling of 979 KB (85% of the 1,152 KB transfer ceiling), and
`tools/perf_check.mjs` fails the build if it exceeds it.

The deltas above are computed from the two ends of the table rather than
carried forward, because the version of this table written on 2026-10-20
listed +679/+376/+93, which matched neither its own baseline nor its own
head. The artifact has also grown since the report was filed - the
readable build moved from 1,976 KB to 1,978 KB when `PS.VERSION` and the
changelog entry for this release were added - which is exactly why these
figures are re-quoted from `npm run perf` rather than remembered.

**The ceiling was wrong.** ADR 0001 said "3 seconds on 4G". The
implementation picked 1.5 Mbps, which is 3G territory, and turned that
into a 576 KB ceiling. It was six times tighter than the trigger it
came from, and it was a number nobody could derive. It is now 3 Mbps
- still well below the 10 to 25 Mbps median Ookla reports for 4G -
which gives 1,152 KB. `build.mjs`, `tools/perf_check.mjs` and
`tools/build_min.mjs` all compute it from seconds times rate, so the
ceiling and its reason cannot drift apart again.

The plan's reclaim table predicted ~45-55 KB of savings from
refactoring. The actual reclaim was smaller, and it did not matter,
because the ceiling was never the binding constraint. **The real
constraint on this product is now the reader's time and the
maintainability of the code, not the byte ceiling.** 605 KB of
gzip headroom is roughly 2.1 MB of further source.

### Known and accepted

- The searchable content is English-authored. The application shell is
  fully translated across English and Spanish: 2 locales registered, 44
  catalog keys, all 44 wired (`npm run audit:i18n`). The limit is the
  catalog's breadth, not its wiring - 44 shell strings against 234
  English-authored content records.
- Credentials are deliberately not issued. ProcureSherpa is not a
  legally authorised credential issuer and says so.
- The workbenches are workpapers, not a system of record. The receipt
  workpaper finds the variance and does not release a payment. The
  approvals workbench records a delegation of authority and does not
  route an approval or block a purchase. The RFx workbench produces an
  award recommendation and does not constitute a tender.
- There is no `og:image`, because generating an honest 1200x630 asset
  would mean a rasterizer dependency for one image.

### External dependencies

**None that reach a user.** No server, no APIs, no runtime dependencies:
`dependencies` in `package.json` is empty and stays empty. There are
**three dev-dependencies** - `eslint` (the lint step), `jsdom` (every
headless test in the suite) and `terser` (the minified deploy build) -
and none of them ships: they install on a build machine and never enter
the artifact. `npm audit` reports 0 vulnerabilities against those three
and their trees, and `node tools/preflight.mjs` guards the `minimatch`
override that holds it there; see SECURITY.md, "Dependency status".

The report this section corrects said `terser` was the only
dev-dependency. It was true of the change ADR 0001 made, not of the
manifest: `eslint` and `jsdom` were already there.

## 9a. Wave 7 - the second review

Three things came out of a second pass over the product, and all three
were wrong in ways the first pass had missed.

### The curriculum was scattered, and the gate protected it

The Academy reordered its modules by the profile role. A buyer saw
**Module 7, 9, 2, 1, 3, 4, 5, 6, 8, 10, 11** while every badge still
read its own number. Only the default profile got 1 to 11, and the
default is what every screenshot and every check had used.

The root cause was not the reordering, it was the method. The gate
G13 was written from the feature rather than from the requirement, so
it asserted that the role *reordered* the curriculum - it protected
the defect. G13 now states the requirement in the requirement's words.

| | Before | After |
|---|---|---|
| Module order | Role-dependent, scattered for 4 of 5 roles | **1 to 11, always** |
| Role's effect | Reordered the curriculum | **Recommends modules, in module order** |
| Resume target | Last opened, so it never moved | **First uncompleted function** |
| Expert learning path | 4, 10, 10, 10, 8, 8 | **4, 8, 8, 10, 10, 10** |
| All-modules table | Grouped by track | **Sorted by module number, with a Module column** |

### The menu had a two-option field and ignored it

The profile has carried a `track` since it was added. It changed one
line of text. The sidebar was a flat 39 items for everybody.

| | Learn view | Work view |
|---|---|---|
| Sections | Start, Learn, Library, Look It Up, My Work | Start, Workbench, Toolkit, Library, Look It Up, My Work |
| Items | **26** | **30** |

The reference library is shared between the two views on purpose: the
Academy is taught through the SOPs, templates and calculators, and
every Academy function links into them. A **Learn / Work** switch in
the sidebar writes the same `profile.track` field the profile modal
writes, so there is one source of truth. The current route always
wins, so the menu is never a dead end.

This changed a documented rule rather than breaking one. `src/README.md`
said not to reintroduce a hub-switcher, and I had been quoting that
rule as though it came from ADR 0001. It did not - ADR 0001 is about
the single-file architecture and says nothing about the sidebar. The
rule's actual reasons were two specific implementation failures. It
is now rewritten with what it should have said, and the reason it
changed is recorded there rather than quietly overwritten.

### The explanation did not carry its example

A case study lived in the 'Think' tab, so somebody reading how landed
cost works never met an example of landed cost working. The example
is now in the 'Learn' tab, in the middle of the explanation, and the
worked example links to the calculator with `?example=1` so the
reader arrives at a finished calculation rather than an empty form.

The calculators already had curated example data and a Load example
button. What was missing was the ability to explore: **Random
values** perturbs the example by enough to change the answer and
little enough that the figures still look like procurement, while
respecting every rule the field declares.

### What the tests caught

- **G11, the reachability gate**, collected its inbound links from the
  rendered sidebar, so scoping the menu made the three workbench
  routes look like orphans. A route is reachable if it is reachable in
  the view it belongs to, so the gate now checks both views.
- **Seven navigation icons became literal question marks.** The file
  was written through a PowerShell pipe whose encoding was not UTF-8,
  and it ate the Unicode symbols. The page still rendered and every
  test still passed; the sidebar just looked like it had a font
  problem. The icons are Unicode escapes now, and a gate fails the
  build on a question mark where a symbol belongs.
- **The navigation was built once at boot and never rebuilt on
  navigation.** The rule that the current route always wins did not
  work: a first load of any workbench page had a menu that did not
  contain the page. The cause of my missing it is the more interesting
  part: the test for the rule called `PS.buildNav()` by hand before it
  looked at the menu, so it passed while the product was broken. The
  test was checking that the function worked, not that the product
  worked. The gate now sets the hash and lets the router do the work,
  and a separate gate walks every route in both views to check that
  the section owning the page is on screen while you are on it.
- **A dead call to a deleted function** was left in the Academy hub.
  It worked by accident, because the function was gone. It read like
  the reordering was still there, which is exactly the kind of line
  somebody re-enables a year later without meaning to.

## 9b. The CI that was failing for the wrong reason

The Actions tab was red on every push, with the annotation "The job
was not started because recent account payments have failed or your
spending limit needs to be increased". That message was true of the
account, and it is the thing everybody on this project expected to
see, so it was read as the billing block every time. It was not the
whole story.

**The Deploy workflow had never compiled.** It failed in zero seconds
with no jobs at all, and the reason was one line:

    jobs:
      deploy:
        if: ${{ secrets.VERCEL_TOKEN != '' }}

`secrets` is not an allowed context in `jobs.<job_id>.if`. The allowed
contexts there are `github`, `needs`, `vars` and `inputs`. A workflow
that uses `secrets` in that position fails to compile before a job is
created, and GitHub reports it as "This run likely failed because of
a workflow file issue". The billing annotation was attached to the
run that never had a job, so the real cause was invisible under a
real cause that was also present.

The token check moved to a step, where `secrets` is allowed. There is
a new gate for it, `npm run check:workflows`, because a failure that
invisible should not be able to happen twice.

**The account's block is intermittent, and it came back.** A push-triggered QA run
and a scratch repository's CI both passed at the same time, so the
block was not account-wide and the repository's public visibility was
not what was holding Actions back. Two minutes later the next push was
blocked again, and the artifact upload started failing with "Artifact
storage quota has been hit", which is the same account billing arriving
from a different direction.

So the suite now runs on a **self-hosted runner**: the workstation that
develops the project, registered against this repository only, started
on login. A self-hosted runner does not consume hosted minutes, so it is
not subject to the block at all. The trade is the obvious one - CI needs
that machine to be awake - and the way back is one line in each
workflow once the billing is fixed.

**The trade was paid within days.** As at 2026-11-01 that runner is
**offline** (`gh api repos/chandrahotha/Procure_Sherpa/actions/runners`),
the scheduled run of 2026-10-26 queued for 24h0m2s and was cancelled by
GitHub's own limit without a single step running, the Deploy run that
waits on it was skipped on 2026-10-27, and the last push CI actually
verified was run 51 on 2026-10-21. A queued job is neither red nor green,
and the badge reports the most recent attempt rather than the state of
the code, so a badge can read passing while nothing has run and failing
while the same commit sits unverified. `npm run qa` locally is the gate
with a real exit code; see CONTRIBUTING.md, "CI is green because nothing
ran".

**Two things about the runner were not obvious.** The first was the
shell. A hosted Linux runner runs bash and a self-hosted Windows runner
runs PowerShell, and asking for bash on the Windows one finds the WSL
shim in System32 and fails with "execvpe(/bin/bash) failed" where WSL
is not installed. The workflow now decides the release path in Node and
names no shell at all, so it cannot matter which one the runner picks.
The second was the artifact upload, which is a convenience and not part
of the gate, and which was failing the run after the whole suite had
passed. It is now reported and not enforced.
**The deployment is now gated by the gate.** The workflow runs on
`workflow_run` of the QA workflow and only proceeds if the gate
passed, so a commit that fails QA is never published. A badge that
says passing and a live site three commits behind are the same
failure in two places.

**The build carries a stamp.** `PS.BUILD` is a hash of the source
fragments. A hash of the commit could not work, because committing
the artifact changes the commit; a hash of the artifact would be
circular. A hash of the sources is stable, so the committed artifact
always matches a rebuild, and the live site can be asked whether it
is serving the build it is supposed to be. `npm run verify:deploy`
answers that, and the Deploy workflow waits for the deployment to
land before it asks, because a deployment is not live the instant
the gate finishes.

Two things about the stamp are worth recording, because both were
bugs that passed everything. The stamp reader matched single quotes
only, and the minifier rewrites string literals, so it could read the
artifact nobody deploys and not the one everybody does. And the
verify step ran before Vercel had finished building, so it checked
the previous deployment and called it a failure of the build on its
way. A gate on the stamp now checks both the readable and the
minified form, because a stamp that survives one and dies in the
other works in development and not in production.

## 10. What I would do next

1. **The Library Hub.** The Operations Hub was derived from the
   registry, which fixed its coverage, but the nine content types are
   still nine separate list pages. One filterable cross-type library
   with a facet for type, domain, and lifecycle phase would be the
   single most useful addition left, and the registry already has
   everything it needs.
2. **Print stylesheet for the workbenches.** The records export to
   CSV but not to a paper workpaper. A procurement file that has to be
   printed for an audit is a real use case.
3. **The last sandbox.** This item used to say the eleven hand-written
   crisis sandboxes in `08g1` were the largest remaining duplication and
   should be collapsed into one declarative table and one renderer. That
   has since been done: `src/core/08g1a_sandbox_models.js` now holds 10
   declarative crisis models and `PS.renderSandboxForm()` draws all of
   them from one shape, so a new sandbox is a data change. What is left
   is the gap the refactor exposed rather than closed: the Academy maps
   its functions onto **11** crisis types, and the eleventh,
   `price-increase`, is the fallback that every unmapped function gets.
   It has an evaluation branch in `PS.executeAcademySandbox()` but no
   field model in the table, so `renderSandboxForm()` returns an empty
   string and those functions render a sandbox card with no inputs.
   Adding the missing model is a data change and would make the count
   honest at 11. (A comment in the same file still says "the eleven
   crisis models"; the file holds ten.)
4. **Making the Vercel path automatic.** Every one of the eleven
   deploys in this revamp was a manual `npm run deploy` from a
   git-free staging copy. It works, but it is a person remembering to
   run a command, and the Git integration should be the normal path.
